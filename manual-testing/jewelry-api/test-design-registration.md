# 🎯 Применение техник тест-дизайна · Регистрация пользователя

| | |
|---|---|
| **Объект** | `POST /api/v1/auth/register` |
| **Основание** | Аналитика ювелирного магазина, REST API, версия 0.3 от 12.09.2026 |
| **Автор** | Хряпин Г.С. |
| **Дата** | 12 сентября 2026 |

**Контракт из документа (раздел 4.3):**
```json
{ "email": "user@example.com", "phone": "+7 999 999 99 99", "password": "StrongPassword123!" }
→ 201 { "id": "...", "email": "...", "phone": "+79999999999", "status": "PENDING_VERIFICATION" }
```

## ⚠️ Допущения

Политика пароля и ограничения длины полей в документе v0.3 не описаны. До уточнения по Swagger приняты допущения:

| № | Допущение | Основание |
|:-:|---|---|
| Д-1 | Пароль: 8–64 символа | Типовая практика, требует подтверждения |
| Д-2 | Пароль: обязательны строчная, заглавная и цифра | Текст сообщения API: `must contain lower, upper and digit` |
| Д-3 | Email: максимум 254 символа | RFC 5321 |
| Д-4 | Телефон: `+7` и 10 цифр, итого 11 цифр | AUTH-01 п.3, формат нормализации `+79999999999` |

## 1. Эквивалентное разделение

**Где применяем:** поля `email`, `phone`, `password`.
**Почему:** у каждого поля бесконечное множество входных значений. Разбиваем на группы, внутри которых система ведёт себя одинаково, и проверяем по одному представителю.

### 1.1. Поле `email`

| Класс | Тип | Представитель | Ожидание | Источник |
|---|:-:|---|---|---|
| Корректный адрес | ✅ | `qa1_main@example.com` | 201 | док 4.3 |
| Верхний регистр | ✅ | `QA1_CASE@EXAMPLE.COM` | 201, нормализован | AUTH-01 п.3 |
| Отсутствует `@` | ❌ | `qa1test.example.com` | 400 `VALIDATION_ERROR` | док 4.4 |
| Два `@` | ❌ | `qa1@@example.com` | 400 | док 4.4 |
| Нет локальной части | ❌ | `@example.com` | 400 | док 4.4 |
| Нет домена | ❌ | `qa1_test@` | 400 | док 4.4 |
| Нет доменной зоны | ❌ | `qa1_test@example` | 400 — письмо недоставляемо, AUTH-02 недостижим | AUTH-01 п.7 |

## 2. Анализ граничных значений

**Где применяем:** длина телефона, длина пароля, длина email.
**Почему:** ошибки чаще всего живут на стыке классов — разработчик пишет `<` вместо `<=` (ошибка на единицу). Середина диапазона таких дефектов не ловит.

### 2.1. Количество цифр в телефоне (норма — 11)

| Значение | Цифр | Ожидание |
|---|:-:|---|
| `+7999111223` | 10 | 400 |
| `+79991112233` | **11** | **201** |
| `+799911122334` | 12 | 400 |

### 2.2. Длина пароля (по Д-1: 8–64)

| Значение | Длина | Ожидание |
|---|:-:|---|
| `Strng12` | 7 | 400 |
| `Strong12` | **8** | **201** |
| `Strong123` | 9 | 201 |
| 64 символа, правила соблюдены | **64** | **201** |
| 65 символов | 65 | 400 |

### 2.3. Длина email (по Д-3: 254)

254 символа → 201 · 255 символов → 400 · 10 000 символов → 400, **не 500 и не таймаут**.

**Где применяем:** сочетание условий «формат валиден × email уникален × телефон уникален».
**Почему:** результат зависит не от одного условия, а от их комбинации. Таблица гарантирует, что ни одно сочетание не потеряно.

## 4. Попарное тестирование

**Где применяем:** независимые параметры представления данных.
**Почему:** к парам «валидный / невалидный» техника не подходит — первое же невалидное поле даёт `400` и маскирует остальные. Берём параметры, которые не отменяют друг друга, и проверяем нормализацию.

**Параметры:**
- Формат телефона: `+7 999 …` · `+79991112233` · `89991112233`
- Регистр email: нижний · ВЕРХНИЙ · Смешанный
- Пробелы по краям email: есть · нет

Полный перебор — 18 комбинаций, попарно — **9**.

| # | Формат телефона | Регистр email | Пробелы | Ожидание |
|:-:|---|---|:-:|---|
| 1 | `+7 999 …` | нижний | нет | 201, телефон нормализован |
| 2 | `+7 999 …` | ВЕРХНИЙ | есть | 201, email приведён к нижнему |
| 3 | `+7 999 …` | Смешанный | нет | 201 |
| 4 | `+79991112233` | нижний | есть | 201 |
| 5 | `+79991112233` | ВЕРХНИЙ | нет | 201 |
| 6 | `+79991112233` | Смешанный | есть | 201 |
| 7 | `89991112233` | нижний | нет | Поведение уточнить |
| 8 | `89991112233` | ВЕРХНИЙ | есть | Поведение уточнить |
| 9 | `89991112233` | Смешанный | есть | Поведение уточнить |

В каждом тесте телефон и email уникальны (`qa4_1@…`, `qa4_2@…`), проверяется нормализация в ответе.

## 5. Диаграмма состояний и переходов

**Где применяем:** жизненный цикл учётной записи.
**Почему:** регистрация — не отдельное действие, а вход в цепочку статусов. Дефекты живут в недопустимых переходах.

**Состояния:** `PENDING_VERIFICATION` → `ACTIVE`, отдельно `BLOCKED` и `DELETED` (док 4.1).

### 5.1. Допустимые переходы

| Из состояния | Событие | Результат | Источник |
|---|---|---|---|
| — | register | `PENDING_VERIFICATION` | AUTH-01 п.5 |
| `PENDING_VERIFICATION` | verify-email валидным токеном | `ACTIVE`, `emailVerified=true` | AUTH-02 |
| `ACTIVE` | block | `BLOCKED` | док 4.3 |
| `BLOCKED` | unblock | `ACTIVE` | док 4.3 |
| `ACTIVE` / `BLOCKED` | delete | `DELETED` (soft) | док 4.3 |

### 5.2. Недопустимые переходы и запреты

| Состояние | Действие | Ожидание | Источник |
|---|---|---|---|
| `PENDING_VERIFICATION` | login | **403 `EMAIL_NOT_VERIFIED`** | док 4.4 |
| `ACTIVE` | verify-email тем же токеном повторно | Ошибка, токен одноразовый (`usedAt`) | AUTH-02 п.4 |
| `BLOCKED` | login | **403 `ACCOUNT_BLOCKED`** | док 4.4 |
| `BLOCKED` | refresh выданным ранее токеном | 401, доступ не продлевается | док 4.1 |
| `DELETED` | login | Доступ закрыт | док 4.1 |
| `DELETED` | register на тот же email | ❓ **Не описано** — вопрос аналитику | — |

## 6. Предугадывание ошибки

**Где применяем:** структура запроса, а не значения полей.
**Почему:** валидацию значений разработчик обычно пишет, а про чужой тип данных, лишнее поле и повторную отправку забывает.

| № | Проверка | Чего опасаемся | Ожидание |
|:-:|---|---|---|
| 6.1 | Лишнее поле `"role": "SUPER_ADMIN"` | 🔴 Назначение роли из запроса = захват админки | Поле игнорируется, роль `USER` |
| 6.2 | Лишнее поле `"status": "ACTIVE"` | Обход подтверждения email | Игнорируется |
| 6.3 | Тот же запрос дважды подряд | Дубль пользователя, гонка | Второй → 409 |
| 6.4 | Повторная регистрация на email в статусе `PENDING_VERIFICATION` | Дубль либо потеря первого токена | Поведение уточнить |
| 6.5 | `"email": null` | Падение сервера | 400, **не 500** |
| 6.6 | `"email": 12345` (число) | Падение при приведении типа | 400, **не 500** |
| 6.7 | `"email": ["a@b.ru"]` (массив) | Падение | 400, **не 500** |
| 6.8 | Тело не JSON, а текст | Падение парсера | 400 | 
| 6.9 | SQL-инъекция: `qa' OR 1=1--@ex.com` | Инъекция, утечка | 400, никаких следов SQL | 
| 6.10 | XSS: `<script>alert(1)</script>@ex.com` | Хранимый XSS | 400 либо экранирование |
| 6.11 | Эмодзи в email | Падение кодировки | 400, **не 500** |
| 6.12 | В ответе присутствует `passwordHash` | 🔴 Утечка чувствительных данных | Только поля контракта |
| 6.13 | Ответ об ошибке без поля `code` | Нарушение контракта раздела 4.4 | `code` присутствует |
