## 1. Цель тестирования

Проверить соответствие реализованного backend согласованным требованиям версии 0.3 и выявить дефекты до подключения реального заказчика.

**Задачи:**
1. Проверить функциональность реализованных сервисов по документации
2. Проверить соблюдение контракта API: коды ответов, структура ошибок, схемы данных
3. Проверить разграничение прав доступа между ролями
4. Выявить расхождения между документом v0.3 и фактическим поведением
5. Зафиксировать вопросы к аналитике там, где поведение не описано

## 2. Область тестирования

### 2.1. Что входит

| Сервис | Приоритет | Обоснование |
|---|:-:|---|
| **Auth Service** | 🔴 1 | Приоритет 1 по документу, п. 1.2. Без него недоступно всё остальное |
| **Управление менеджерами** (SUPER_ADMIN) | 🔴 1 | Входит в Auth, критично для разграничения прав |
| **Admin / Catalog Service** | 🟡 2 | Приоритет 1 по документу, зависит от авторизации |
| **Import Service** | 🟢 3 | Проверяется после каталога |

**Виды тестирования:**
- Функциональное: позитивные и негативные сценарии
- Контрактное: соответствие кодов ответов и структуры разделам 4.4 и 16.3
- Тестирование прав доступа по матрице ролей (раздел 3)
- Базовые проверки безопасности: инъекции, утечка полей, доступ к чужим данным
- Проверка бизнес-сценариев AUTH-01 … AUTH-05

### 2.2. Что НЕ входит и почему

| Не тестируем | Причина |
|---|---|
| Pricing, Shopping, Order, Payment, Delivery, Notification | По п. 1.2 документа описаны как целевая модель, разработка не начата |
| Нагрузочное тестирование | Учебный стенд, нагрузка не предусмотрена постановкой |
| Frontend и Admin UI | Отсутствуют, тестируется только backend |
| Интеграция с СДЭК и платёжным провайдером | На первой версии симулируется, внешние системы недоступны |
| Тестирование производительности БД, S3 | Нет доступа к инфраструктуре |
| Проверка почтовых писем | 🔴 Нет доступа к почтовому ящику — см. риск Р-1 |

## 3. Подход

### 3.1. Последовательность

```
Этап 1 · Auth Service          → регистрация, верификация, login, токены
Этап 2 · Права доступа         → матрица ролей, управление менеджерами
Этап 3 · Admin / Catalog       → CRUD товаров, варианты, категории
Этап 4 · Import                → загрузка CSV, статусы задач, ошибки
Этап 5 · Ретест и регресс      → перепроверка исправлений
```

Переход к следующему этапу — после закрытия блокирующих дефектов предыдущего.

### 3.2. Техники

| Техника | Где применяется |
|---|---|
| Эквивалентное разделение | Поля email, phone, password: валидные и невалидные классы |
| Граничные значения | Длина полей, пагинация (`size`, максимум 100), количество символов |
| Таблица решений | Комбинации «статус пользователя × наличие токена × роль» |
| Состояния и переходы | `PENDING_VERIFICATION → ACTIVE → BLOCKED → DELETED`, статусы ImportJob |
| Попарное тестирование | Роль × эндпоинт × наличие токена |
| Предугадывание ошибки | Повторное использование токенов, лишние поля в теле, неверные типы |

### 3.3. Принцип обоснования

У каждого ожидаемого результата указывается источник: пункт документа, схема Swagger или стандарт.
**Если источника нет — заводится не дефект, а вопрос аналитику.**

## 4. Распределение работ (10 тестировщиков)

Зоны закрепляются, чтобы исключить дубли. Внутри зоны тестировщик отвечает за полноту покрытия.

| № | Зона | Эндпоинты |
|:-:|---|---|
| 1 | Регистрация | `POST /auth/register` |
| 2 | Подтверждение email | `POST /auth/verify-email` |
| 3 | Вход | `POST /auth/login` |
| 4 | Токены | `POST /auth/refresh`, `/auth/logout` |
| 5 | Профиль | `GET /users/me` |
| 6 | Менеджеры: создание и список | `POST`, `GET /admin/managers` |
| 7 | Менеджеры: блокировка и удаление | `block`, `unblock`, `DELETE` |
| 8 | 🔴 Права доступа | Все эндпоинты × все роли |
| 9 | Каталог: товары | `/admin/products` |
| 10 | Каталог: категории и варианты | `/admin/categories`, `/variants` |

**Ротация:** после первого прохода зоны меняются по кругу. Свежий взгляд находит то, что замылилось — принцип «парадокс пестицида».

## 5. Окружение и доступы

### 5.1. Требуется от разработчика

- [ ] Учётная запись **SUPER_ADMIN** — иначе зоны 6, 7, 8 непроверяемы
- [ ] Учётная запись **MANAGER**
- [ ] Доступ к почте или тестовый режим выдачи токена подтверждения
- [ ] Подтверждение, можно ли чистить данные и создавать тестовых пользователей
- [ ] Актуальная схема Swagger, синхронная с документом v0.3

### 5.2. Тестовые данные

Соглашение об именовании, чтобы не мешать друг другу:

```
email:  qa<номер зоны>_<цель>@example.com   →  qa1_dup@example.com
phone:  +7900<номер зоны>NNNNNN             →  +79001000001
пароль: StrongPassword123!
```

## 6. Процесс работы с дефектами

### 6.1. Обязательные поля

Эндпоинт и метод · заголовок · тело запроса целиком · ожидаемый результат **со ссылкой на пункт документа** · фактический результат с кодом ответа · severity · окружение.

### 6.2. Шкала severity

| Severity | Когда | Пример на этом проекте |
|---|---|---|
| **Blocker** | Функция недоступна, тестирование остановлено | Сервис не отвечает, login не выдаёт токен |
| **Critical** | Нарушение прав доступа, потеря или утечка данных | USER получает доступ к `/admin/managers`; в ответе есть `passwordHash` |
| **Major** | Функция работает неверно, обхода нет | Валидация телефона пропускает буквы; refresh не отзывается при ротации |
| **Minor** | Функция работает неверно, есть обход | Неверный код ответа при корректной бизнес-логике |
| **Trivial** | Косметика | Опечатка в тексте сообщения |

**Priority определяет разработчик или преподаватель**, тестировщик предлагает.

### 6.3. Порядок

1. Проверить, что дефект воспроизводится дважды
2. Проверить, что его ещё не завели коллеги
3. Отправить в общий чат по шаблону
4. После исправления — **ретест** и, если затронута смежная функциональность, регресс

## 7. Критерии

### 7.1. Критерии начала

- Стенд доступен, Swagger открывается
- Получены учётные записи SUPER_ADMIN и MANAGER
- Документация версии 0.3 роздана участникам

### 7.2. Критерии завершения этапа

- Пройдены все проверки чек-листа по зоне
- Дефектов уровня Blocker и Critical не осталось открытых
- Все найденные дефекты оформлены и переданы
- Открытые вопросы к аналитике зафиксированы списком

### 7.3. Критерии приостановки

- Стенд недоступен более суток
- Выкатывается новая версия — тестирование приостанавливается до появления описания изменений

## 8. Риски

| № | Риск | Влияние | Мера |
|:-:|---|---|---|
| Р-1 | Нет доступа к почте → сценарий подтверждения email непроверяем | 🔴 Высокое | Запросить тестовый режим или доступ к логам |
| Р-2 | Нет учётной записи SUPER_ADMIN → блок прав доступа непроверяем | 🔴 Высокое | Запросить у разработчика до старта |
| Р-3 | Десять человек без трекера → дубли и потери | 🟡 Среднее | Закрепить зоны, вести общий журнал находок |
| Р-4 | Документ описывает целевую модель, часть сервисов не реализована | 🟡 Среднее | Перед заведением дефекта сверяться со Swagger |
| Р-5 | Расхождение документа и Swagger | 🟡 Среднее | Фиксировать как отдельный дефект документации |
| Р-6 | Политика пароля не описана | 🟢 Низкое | Вопрос аналитику, до ответа проверять по Swagger |
| Р-7 | Сервер периодически недоступен | 🟡 Среднее | Заранее готовить коллекции и чек-листы офлайн |
